# **1 文档解析**

> 把各种格式的原始文档，转成**结构化的文本**（最好是 Markdown），并且把标题层级、表格、阅读顺序这些信息保留下来。
>
> ★ 这一节是 RAG 的第一步，也是**唯一一步"做错了后面全救不回来"**的环节。

## **1.1 为什么文档解析是 RAG 最容易被忽略、也最要命的一步**

> **Garbage In, Garbage Out。**
>
> 解析错了，后面 chunking 再合理、embedding 再强、rerank 再准、LLM 再聪明，都救不回来——因为正确的信息**根本没进入向量库**。

对比一下失败的代价：

```
解析错了
   ↓
chunk 是错的
   ↓
embedding 是错的
   ↓
检索永远召不回正确内容
   ↓
LLM 只能编       ← 表现为"幻觉"，但根因在第一步
```

**关键认知**：一个"LLM 答错了"的问题，根因可能在链路的最前面。如果你只在 prompt 上找原因，会找很久都找不到。

★ 还有一层容易被忽略：**解析质量直接决定 chunking 的质量上限**。

```
如果你的解析结果是：
"1. 用户注册 1.1 手机号注册 1.2 邮箱注册 2. 用户登录 2.1 密码登录"
​
    ↓  那"按语义结构切分"根本无从下手
    ↓  因为层级信息在解析阶段就丢了
​
如果你保留成：
# 1. 用户注册
## 1.1 手机号注册
## 1.2 邮箱注册
​
    ↓  才能按标题层级切成"标题 + 内容"的 chunk
```

> 所以「Chunking」章节里讲的"按语义结构切分"、"把标题路径拼进 chunk"，**前提是解析阶段把标题层级保留下来了**。这两章是一条链上的。

## **1.2 ★ 最重要的认知：PDF 内部不是文本**

> PDF 存储的不是"段落和标题"，而是「**在坐标 (x, y) 处画这个字符**」。

这解释了几乎所有 PDF 解析的怪现象：

**现象根因**双栏 PDF 解析出来每行是两栏混在一起的它是按"绘制顺序"而不是"阅读顺序"输出的复制出来的文字没有换行、没有段落PDF 里根本没有"段落"这个概念表格变成一堆散落的数字表格是靠线条画的，不是结构化的两个词中间多个空格 / 粘连字符间距不是空格，是坐标距离

所以**文档解析的本质是"逆向工程"**：

```
原始文档（有人类看的视觉结构）
        ↓  解析器要做的事
推断出：阅读顺序、标题层级、段落边界、表格结构
        ↓
结构化文本（有机器能理解的结构）
```

> ★ **这是本节最该记住的一句**：解析不是"把文字提取出来"，而是**把视觉结构还原成语义结构**。只提取文字的解析器（比如 `pdf.extract_text()`）几乎一定会丢失结构。

## **1.3 各格式的坑**

### **1.3.1 PDF**

**1. 阅读顺序（双栏/多栏）**

```
双栏 PDF 的视觉布局：
┌─────────────┬─────────────┐
│ 左栏第 1 行  │ 右栏第 1 行  │   ← 按 y 坐标排序会得到这两行相邻
│ 左栏第 2 行  │ 右栏第 2 行  │   ← 但正确的阅读顺序是先读完左栏
│ 左栏第 3 行  │ 右栏第 3 行  │
└─────────────┴─────────────┘
​
错误解析结果：
"左栏第1行 右栏第1行 左栏第2行 右栏第2行 ..."   ← 每个句子都被腰斩
```

这是 PDF 解析最经典的坑，也是最难修的。检测方法：打印解析结果，看句子是否在奇怪的地方断开。

**2. 表格**

```
PDF 里表格的三种情况：
├─ 有线框（好处理）   → 可以靠线条检测出来
├─ 无线框（难点）     → 只能靠文字对齐关系推断
└─ 跨页表格（最麻烦） → 同一个表被分到两页，要合并
```

表格必须转成 **Markdown 表格或结构化数据**，不能是一堆散落的数字：

```
❌ 解析结果：
销售额 2024 1200 2025 1500 华东 800 900
​
✅ 解析结果：
| 区域 | 2024 | 2025 |
|---|---|---|
| 华东 | 800  | 900  |
| 总   | 1200 | 1500 |
```

**3. 页眉页脚与页码（每页都重复）**

每页都出现的"XX公司内部资料 第 3 页"会污染 embedding——它让所有 chunk 都多了一段完全相同的噪声，影响相似度计算。

```
去除思路：
├─ 位置过滤   —— 页面顶部/底部固定区域的内容直接丢
├─ 频次统计   —— 在超过 80% 的页面里都出现的短行 → 判定为页眉页脚
└─ 正则匹配   —— "第 \d+ 页"、"Page \d+ of \d+"、纯数字行
```

**4. 扫描件 ≠ 文字版（处理方式完全不同）**

```
文字版 PDF  →  里面有字符对象  →  直接提取（快、准）
扫描件 PDF  →  里面只有一张图  →  必须 OCR（慢、会出错）
```

**怎么判断**？粗略方法：尝试提取文本，如果每页提取出的字符数少得可怜（比如 < 100），那基本就是扫描件。

> ★ 扫描件是 OCR 错误的源头，而 OCR 错误会**静默地**降低检索质量——它不会报错，只会让"正确的词"变成"相近的错词"，从而检索不到。

**5. 其他常见问题**

```
├─ 加密 PDF     —— 需要密码，或有些是"禁止复制"权限
├─ 跨页段落     —— 一个句子被切成两半，落在两个 chunk 里
├─ 数学公式     —— 符号和上下标容易被打散
├─ 代码块       —— 缩进被破坏（缩进是代码的语义！）
└─ 水印         —— 变成到处插入的噪声字符
```

### **1.3.2 Word / PPT / Excel**

**格式主要问题**`.docx`相对好处理，保留了样式 → 能识别标题层级。麻烦的是**文本框**和**批注**（内容经常被漏掉）`.ppt`内容天然碎片化（一页一个要点），适合**按页切分**而不是按 token`.xlsx`★ 最难。要问：**一行是一条记录还是一个 chunk？** 通常需要把每行转成"列名: 值"的文本再向量化`.doc`（老版）先无损转成`.docx`（用 LibreOffice），不要用不靠谱的解析库硬读

### **1.3.3 HTML / 网页**

```
要剥掉的东西：
├─ 导航栏 / 侧边栏 / 页脚   ← 和 PDF 的页眉页脚同一个问题
├─ 广告 / 弹窗 / 推荐位
├─ 评论区（通常不是正文）
└─ <script> / <style> 内容
​
要保留的东西：
├─ 标题层级 h1~h6   ← 直接对应 chunk 的 heading path
├─ 表格 <table>
├─ 列表 <ul>/<ol>
└─ 代码块 <pre><code>
```

工具：`trafilatura`（最适合 RAG 的正文提取）、`readability-lxml`、`BeautifulSoup`。

> 注意：**抓取网页做知识库是有合规风险的**，另外网页是会变的（今天解析的内容明天可能就没了）。

### **1.3.4 其他**

```
├─ 邮件（.eml/.msg）—— 要处理引用链和签名，否则每次回复的原文都会被重复入库
├─ JSON / YAML      —— 要考虑怎么"拍平"成文本，保留 key 路径作为上下文
├─ Markdown         —— 最省事，结构本来就是显式的（所以它是理想的中间格式）
└─ 代码文件          —— 按函数/类切分比按行切分合理得多
```

## **1.4 ★ 统一目标：转成"LLM 友好"的格式**

不管源格式是什么，**统一转成 Markdown** 是实践中最优的选择。原因：

```
Markdown 的好处：
├─ 标题层级显式（#/##/###）    ← Chunking 章节要用的 heading path 靠它
├─ 表格能表达
├─ 列表能表达
├─ 纯文本，无二进制依赖
└─ LLM 天然熟悉（训练数据里大量 Markdown）
```

> ★ 所以字段设计的正确姿势是：
>
> ```
> ❌ { "text": "用户注册 手机号注册 邮箱注册 ..." }        # 结构全丢
> ​
> ✅ { "text": "## 1.1 手机号注册\n用户可以通过手机号...",   # 保留结构
>   "heading_path": "用户注册 > 手机号注册",              # 给检索和过滤用
>   "source": "手册.pdf",
>   "page": 12 }
> ```

**为什么元数据要和正文一起存**：后面「元数据过滤」章节要用（按来源、时间、权限过滤），「Context 组装」也要用它来做引用标注。**解析阶段不存，后面就补不回来了。**

## **1.5 工具选型**

**工具定位适合场景**`PyMuPDF` (fitz)PDF 底层库，可控性最强需要精细控制、自己写规则`pdfplumber`表格提取好表格是重点的 PDF**`MinerU`** / `Marker`PDF → Markdown，**保留结构**★ PDF 为主的项目，首选`unstructured`格式覆盖最广（几乎什么都能读）快速起步、格式杂`LlamaParse` / `Document AI`云服务扫描件多、有预算、想省事`trafilatura`网页正文提取抓网页做知识库

**一个务实的组合建议**：

```
第 1 步：全部用 unstructured 跑一遍，快速把流程打通
第 2 步：找出解析效果最差的那类文档（通常是 PDF）
第 3 步：针对那类文档换成专用工具（MinerU / Marker）
```

> 不要一开始就追求"最优解析器"。**先用最粗糙的方案跑通端到端，再用评测集定位哪类文档解析最差，然后针对性换工具。** 这和你笔记里"用便宜的方法粗筛、再用昂贵的方法精排"是同一个思路。

**决策树**：

```
文档是什么格式？
├─ 扫描件/图片  → 必须 OCR（云服务最省事）
├─ PDF
│   ├─ 表格多   → pdfplumber / MinerU
│   ├─ 双栏论文 → MinerU / Marker（基于模型，能理解版面）
│   └─ 结构简单 → PyMuPDF 自己写规则
├─ 网页        → trafilatura
├─ Office      → unstructured / 官方 SDK
└─ Markdown    → 直接用，不用解析
```

## **1.6 ★ 解析质量怎么评测**

> 解析质量必须在**单独这一层**被评测。因为如果你只在最后测"答案对不对"，你无法区分是解析错了还是检索错了。

**方法：黄金集（Golden Set）**

```
1. 挑 10~20 页最有代表性的文档（覆盖各种版式）
2. 人工写"标准解析结果"（或者人工标注"必须被正确解析出来的关键信息"）
3. 自动化比对，检查这几项：
```

**检查项怎么查为什么重要**表格还原表格是否还是表格表格里的数字检索不到 = 业务问题页眉页脚去除是否还有重复行污染 embedding阅读顺序句子是否在奇怪处断开双栏的核心指标标题层级标题是否被识别成标题决定 chunking 质量上限特殊内容公式/代码块是否完整技术文档的关键OCR 错误率抽样人工看扫描件专用

**一个不需要写代码的自检方法**：

> 直接看解析结果，问自己一句：**"这段文本，我人能读懂吗？我能看出这是文档的哪一部分吗？"**
>
> 如果人读着都觉得句子错乱、不知道在讲哪一章——那 embedding 和 LLM 更读不懂。**解析结果的可读性，就是最直接的评测指标。**

## **1.7 最小可跑的实现**

```
# 伪代码，体现流程而非具体 API
​
def ingest(file_path):
    # 1. 按格式分发到不同解析器
    if is_scanned_pdf(file_path):
        raw = ocr(file_path)                      # 扫描件 → OCR
    elif file_path.endswith('.pdf'):
        raw = pdf_to_markdown(file_path)          # 保留结构的解析
    elif file_path.endswith(('.docx', '.pptx')):
        raw = office_to_markdown(file_path)
    elif file_path.endswith(('.html', '.htm')):
        raw = extract_main_content(file_path)     # 剥掉导航/广告
    else:
        raw = read_text(file_path)
​
    # 2. 清洗：去页眉页脚、去连续空行、统一空白字符
    raw = clean(raw)
​
    # 3. 保留元数据（★ 这一步别省，后面补不回来）
    return {
        "text": raw,                    # Markdown 格式，保留标题层级
        "source": file_path,            # 用于引用标注
        "parsed_at": now(),             # 用于增量更新判断
    }
```

**三个不要省的点**：

```
1. 不要直接把 PDF 提取的纯文本喂给 chunking —— 先转 Markdown
2. 不要丢掉元数据（source / page / heading_path）—— 后面补不回来
3. 不要跳过解析评测 —— 否则你永远不知道瓶颈在解析还是在检索
```

## **1.8 ★ 什么情况算"解析做好了"**

```
□ 表格还是表格（不是散落的数字）
□ 标题被识别成标题（有 # 层级）
□ 双栏没有串行（句子没有被腰斩）
□ 页眉页脚/页码已去除
□ 段落边界正确
□ 代码块缩进完整
□ 元数据（source / page / heading_path）已保留
□ 原文顺序没有乱
```

> 满足这些，后面的 Chunking 才有发挥空间。**不满足的话，先修解析，不要急着调 chunk 大小和 embedding 模型**——那是治标不治本。

## **1.9 和后面章节的关系**

```
文档解析
   ↓ 输出 Markdown + 标题层级 + 元数据
Chunking
   ↓ 利用标题层级做语义切分、拼 heading path
Embedding
   ↓ 对结构良好的 chunk 向量化
向量库（元数据过滤）
   ↓ 利用解析阶段的 source / page / 权限字段做过滤
```

> ★ 一句话总结：**解析质量决定 chunking 的上限，chunking 质量决定检索的上限，检索质量决定 RAG 的上限。** 所以整条链的第一个瓶颈，就在这一节。
