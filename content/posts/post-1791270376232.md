# **1 Embedding**

> Embedding 就是把一个对象转换成一个能够表达其语义特征的高维向量。

## **1.1 为什么需要Embedding**

传统数据库擅长精确查询，但是解决不了找到接近内容的查询，但是 Embedding 可以把数据映射到向量空间，可以通过**向量相似度**寻找最接近的内容。

## **1.2 Embedding 的本质：有损的语义压缩**

> Embedding 保留「语义」，扔掉「字面」。

这决定了它的能力边界：

**查询类型向量检索关键词检索（BM25）**意思相近但用词不同（"如何退款" vs "退货流程"）✅ 强❌ 弱精确标识符（`ERR_4092`、`previous_response_id`、人名、型号）❌**几乎无效**✅ 强

精确标识符（错误码、函数名、人名、产品型号）在语义空间里**没有有效坐标**，所以向量检索对它们天然失效。

**这就是混合检索存在的根本理由——它不是可选优化，而是必需项。**

## **1.3 Embedding 对象**

文本、图片、音频、代码，甚至可以是多模态对象（如图片 + 文本）

## **1.4 向量维度**

向量有多少个数字，如\[0.1, 0.2, 0.3] 是个3维向量，不同的 Embedding 模型可能产生不同维度

## **1.5 向量数据库是什么**

> **向量数据库是存储和检索高维向量的数据库。**
>
> 本笔记后面的所有内容（索引、量化、混合检索……）都是围绕这一个定义展开的。

# **2 向量相似度**

两个向量有多相似？

## **2.1 Cosine Similarity（余弦相似度）**

$$
\cos(\theta) = \frac{A \cdot B}{\|A\| \, \|B\|} = \frac{\sum_{i=1}^{n} A_i B_i}{\sqrt{\sum_{i=1}^{n} A_i^2} \, \sqrt{\sum_{i=1}^{n} B_i^2}}
$$

**符号含义**`A · B`内积（对应位置相乘再求和）`‖A‖`向量 A 的模长（L2 范数）分母把两个向量的长度归一化掉

比较两个向量的方向是否接近，方向接近：cosine similarity ≈ 1, 方向完全相反：≈ -1, 通常情况下越接近1越相似。但要注意:

> 不同的 Embedding 模型、不同任务下，相似度数值不能简单跨模型比较

## **2.2 Euclidean Distance(欧氏距离)**

二维情况下就是两个点之间的直线距离

$$
d(A, B) = \sqrt{\sum_{i=1}^{n} (A_i - B_i)^2}
$$

**符号含义**`A_i - B_i`两个向量在第 i 维上的差求和后开方n 维空间里的直线距离`n`向量维度（如 1536）

距离越小 → 越相似

```
各向量库的 metric 名称：
COSINE → 余弦相似度
L2     → 欧氏距离
IP     → Inner Product，内积
```

## **2.3 三种度量之间的关系**

**余弦相似度、L2 距离、内积在向量归一化后是等价的**，不是三个独立的选项。

当向量做了 L2 归一化（`||v|| = 1`）之后：

```
cos(A, B) = A · B                 # 余弦相似度 = 内积
||A - B||² = 2 - 2·(A · B)         # 欧氏距离² 与内积单调对应
```

结论：**归一化之后，用 cosine、IP、L2 检索，排名结果完全一致**，只是数值尺度和方向不同。

两个实际后果：

0. **很多向量库的 "cosine" 实现就是「入库时归一化 + 检索时算内积」**——因为内积只有乘加运算，可以走 SIMD，没有开方和除法。
1. **归一化必须两侧一致**。用 cosine 时向量库通常自动帮你归一化；用 **IP 时通常不会**。写入归一化了、查询没归一化，召回率会莫名崩掉——这是最常见的踩坑点之一。

> 补充：余弦的数学定义域是 `[-1, 1]`，但**当代文本 Embedding 模型的输出向量基本是非负的**，实际落在 `[0, 1]`，很少见到负值。
>
> "0.8 算不算相似"**必须针对具体模型和数据集标定**，不能背一个阈值到处用。

## **2.4 Embedding 模型**

* OpenAI Embedding（`text-embedding-3-small` / `text-embedding-3-large`）
* Qwen Embedding（`text-embedding-v4`，支持 64~2048 维，默认 1024；`text-embedding-v3` 与 v4 维度兼容）

### **2.4.1 输出维度是可配置的**

现代 Embedding 模型的维度**不是一个固定属性，而是一个可调的旋钮**：

```
OpenAI text-embedding-3 系列 → 用 dimensions 参数指定输出维度
  text-embedding-3-small → 可降到 512
  text-embedding-3-large → 256 / 1024 / 3072
​
Qwen text-embedding-v4 → 64 ~ 2048（默认 1024）
  · 大规模搜索且存储有限 → 选 256 或 512 维
  · 通用场景 → 1024 维
  · 精度要求高 → 1536 或 2048 维
```

这解释了为什么"维度是一个存储与精度之间的权衡"，也解释了后面「模型升级」里那个例外。

# **3 索引**

> 索引的本质就是减少 Query 实际需要比较的向量数量。

## **3.1 Flat Index (暴力索引）**

> 不做任何优化，Query 和所有向量计算距离。
>
> Flat 没有真正的索引结构，它只是存储向量

复杂度：N 个向量，D 维，一次查询 O(N D)

## **3.2 IVF Index**

> 先把向量空间划分成很多区域，搜索时先找到区域，再搜索区域内部。

### **3.2.1 IVF 建索引的过程**

0. 聚类：使用 k-means 算法

例如：将1m vectors 分成 1000 cluster 得到 cluster1: 中心C1,v1,v2,v3 cluster2: 中心C2, v4,v5

这里的C1，C2是**聚类中心**，不是原始向量

2. 建立倒排表（inverted file)

```
Cluster
​
Cluster1
 |
 Vector1
 Vector2
​
​
Cluster2
 |
 Vector3
 Vector4
```

### **3.2.2 IVF 查询过程**

0. 在 Cluster Center 这一层也用轻量索引加速，找出最近的 `nprobe` 个中心。
   > 只写"计算 Query 和所有 Cluster Center 的距离"会漏掉这一步——1000 个中心的距离计算本身也不便宜。
1. 只在这 `nprobe` 个倒排桶内部做精确距离计算，得到 Top-K（桶内依然是暴力比较，这正是它需要和 PQ 组合的原因）。

### **3.2.3 ★ IVF 的核心缺陷：边界问题**

如果真正的近邻落在「中心稍远、但实际很近」的另一个 cluster 里，**IVF 永远找不到它**——不是排在后面，而是**根本不进候选集**。

* `nprobe = 1`：最快，但召回率可能只有 60~80%
* `nprobe ↑`：召回率上升，延迟**线性**上升

> **nprobe 存在的唯一目的就是买召回率。** 这是 IVF 最该理解的一点。

### **3.2.4 关键参数**

* nlist: 有多少个 Cluster（经验值 `nlist ≈ 4 × sqrt(N)`）
* nprobe: 查询时搜索多少个 Cluster（查询时通常搜索多个区域，nprobe > 1)

## **3.3 HNSW Index**

> Hierarchical Navigable Small World：**给向量空间修一座多层立交桥。**
>
> 生产环境的向量检索默认就是它（Milvus / Qdrant / Weaviate / pgvector / Elasticsearch 都把 HNSW 作为首选索引）。
>
> 理由：**它是唯一一个「改一个参数就能在召回率和延迟之间滑动、且不用重建索引」的索引。**

### **3.3.1 结构：多层图**

```
Layer 2  (最稀疏，只有长距离"高速公路"节点)        ●────────●
                                                  │        │
Layer 1  (中等密度)                    ●─────●─────●────●───●
                                      │     │     │    │   │
Layer 0  (包含全部向量，短边密集)  ●─●─●─●─●─●─●─●─●─●─●─●─●─●
```

* **上层稀疏、边很长** → 负责「快速接近目标区域」
* **下层稠密、边很短** → 负责「精确定位」
* 这就是「小世界」性质：任意两点之间只需要很少的跳数就能到达

### **3.3.2 查询过程**

```
1. 从最顶层的入口点出发
2. 当前层贪心搜索：不断走向"离 Query 更近的邻居"，直到没有更近的
3. 下降到下一层，从上一层的终点继续（★ 不是回到起点）
4. 重复 2-3，直到抵达 Layer 0
5. 在 Layer 0 用候选队列做更细致的搜索（宽度 = efSearch），返回 Top-K
```

### **3.3.3 三个参数**

**参数阶段作用典型值影响**`M`建索引每个节点保留多少条边16（常用）/ 32 / 64↑ 召回率↑、内存↑、建索引慢`efConstruction`建索引建图时候选队列宽度100~500（常用 200）↑ 图质量↑、建索引时间↑`efSearch`**查询时**底层搜索候选队列宽度64~512↑ 召回率↑、延迟↑

### **3.3.4 ★ 最该记住的一点：efSearch 是「查询时参数」**

它**不需要重建索引、不需要重启服务**，就能在「快但可能漏」和「慢但更全」之间滑动。

> 线上召回率不够 → 不用重建 60GB 的索引，把 `efSearch` 从 64 调到 128 就能救。

同一份索引可以先以 `efSearch=32` 服务普通请求、用 `efSearch=256` 服务高精度请求。这是 HNSW 相对 IVF 最大的工程优势。

### **3.3.5 代价（决定你什么时候不该用 HNSW）**

* **内存最贵**：除原始向量还要存图结构（每点 ~M 条边）。100 万 × 1536 维纯向量约 6 GB，加 HNSW 图结构通常要 **1.5~2 倍**。这正是 HNSW 常与量化组合使用的原因。
* **建索引慢**：比 IVF 慢得多，且与数据量强相关。
* **删除麻烦**：删点会破坏图的连通性，实现上一般是**标记删除**，空间回收靠 compaction / 定期重建。**高频增删的场景要认真评估维护成本。**

### **3.3.6 与 IVF 对比**

**IVFHNSW**核心假设向量会**成簇**相似向量之间有**可导航的路径**事后调精度能（nprobe，线性变慢）能（efSearch）同延迟下召回率中**高**内存低（可配 PQ）**高**建索引速度快慢高频增删相对友好差（标记删除+ 重建）适用场景超大规模、内存敏感**绝大多数默认场景**

**选型一句话：数据量千万以内、内存不极端紧张 → 直接用 HNSW。**

# **4 Quantization（量化）**

> 把原本精度很高、占空间很大的向量，用更少的比特来表示，从而降低内存和计算成本，但会牺牲一部分精度。

## **4.1 为什么需要 Quantization？**

假设一个 Embedding 为 1536 维度，通常每个维度是 `float32`,4 bytes，那么一个向量 1536 \* 4 B 约为 4KB 了，一千万条向量就是 10M \* 4KB 约为 61GB，而且这只是原始向量，不包括索引，实际会更大，因此需要量化

**但这 61GB 到底能压到多少？** 这才是量化的真正价值所在：

```
原始：1536 维 × 4 B  = 6144 B
SQ  ：1536 维 × 1 B  = 1536 B          →   4x   →  约 15 GB
PQ  ：切 192 段 × 8 维，每段 256 个质心 = 8 bit
      192 段 × 1 B   = 192 B           →  32x   →  约 1.9 GB
      码本额外：192 × 256 × 8 维 × 4 B = 1.5 MB（一次性）
```

> 所以 SQ 只是"小省"，PQ 才是"大省"。只写 float32→int8 会让人误以为 PQ 和 SQ 是一个量级，实际上差了 8 倍。

常见的精度档位：

```
float32 → float16
float32 → int8
```

## **4.2 量化本质上是在干什么？**

> 用低精度的数据，近似表示原来的高精度向量。

当然真正的量化不是简单的从长 bit 位截断成短 bit 位，而是建立一个映射

```
float32
[-1, 1]
​
  ↓
  
int8
[-127, 127]
```

## **4.3 但是为什么不全部使用 int8？**

> 因为有代价：精度损失。

从而使 Recall 率下降。

但"精度损失"只是表层答案，真正的原因是：

> **量化误差会通过「排序」被放大。**
>
> 排名靠前的候选之间，距离差异本来就非常微小。量化带来的噪声，足以把这些微小的差异淹没，从而把顺序打乱。所以损失的不是"距离准不准"，而是"**谁排第一**"。

因此工程上的标准做法不是"用不用量化"，而是**粗筛 + 精排**：

```
压缩向量粗筛（多召回一批，如 top 200）
        ↓
原始向量精排（重算精确距离，取 top 10）
        ↓
（可选）Rerank
```

> ★ 这和后面「Rerank（重排序）」章节其实是**同一个思想在两个层面上的应用**：
>
> * 量化层面：压缩向量粗筛 → 原始向量精排
> * 模型层面：向量检索粗筛 → Cross-Encoder 精排
>
> 理解了这个共性，你就理解了几乎所有"大规模检索系统"的通用结构：**用便宜的方法把候选集缩小，再用昂贵的方法在小子集上求精确。**

## **4.4 几种量化方法**

### **4.4.1 Scalar Quantization（标量量化，SQ）**

> 对向量中的每一个浮点数单独进行压缩。

简单快捷压缩比例高，但有一定精度损失

实现方式：对每一维采样出 `min` / `max`，然后均匀分桶。

```
float32 [-1, 1]  →  int8 [-127, 127]   （256 个桶）
```

### **4.4.2 Product Quantization（PQ）**

把一个高维向量：

```
[ x1 x2 x3 x4 x5 x6 x7 x8 ]
```

拆成几个子向量：

```
[x1 x2] [x3 x4] [x5 x6] [x7 x8]
```

然后**对每一段分别做 k-means 聚类，得到该段的"码本"（codebook）**，每个子向量用「最近质心的编号」来表示。

```
每段的 256 个质心 → 用 8 bit 的编号表示（2^8 = 256）
1536 维切成 192 段 → 192 个 8 bit 编号 = 192 字节
对比原始 1536 维 × 4 B = 6144 字节 → 32x 压缩
```

### **4.4.3 ★ PQ 的精髓：不是"压缩存储"，而是"用查表代替算距离"**

这是 PQ 最该理解的一点。查询时**不需要**把 1536 维的距离真算一遍：

```
第 1 步（一次性建表）：
  Query 与每段的 256 个质心算距离
  192 段 × 256 = 49152 次距离计算
​
第 2 步（每条库内向量）：
  只需查表 192 次 + 求和，就得到近似距离
```

这叫 **ADC（Asymmetric Distance Computation，非对称距离计算）**：Query 保持原始精度，库内向量是压缩码。

> 结论：**PQ 在 FAISS 里是当加速结构用的，不只是用来省内存。** 它同时降低了内存和延迟。

### **4.4.4 ★ IVF + PQ：工业界最经典的组合**

原笔记里 IVF 和 PQ 是两节，但它们的**组合**才是真正落地的形态（FAISS 的代表性配置）：

```
外层 IVF：负责"少算"    —— 把候选从 1000 万缩到几万
内层 PQ ：负责"快算+省内存" —— 桶内用查表代替浮点距离计算
```

因为 IVF 的桶内依然是暴力比较（这是它唯一的短板），PQ 正好补上。

# **5 Chunking**

> 把一个大的 Document 切成适合检索的小块。

为什么不能整个 PDF 生成一个 Embedding？因为整个 PDF -> vector, 表示的是整个 pdf 的语义，如果用户提问：“系统如何处理用户退款？”，拿整个 PDF 的 embedding 去搜索，粒度太粗。

## **5.1 chunk 要多大**

chunk 太小，缺少上下文，chunk 太大，一个chunk包含太多的无用信息，所以 chunk 的大小本质是一个优化问题，要在 Context Completeness 与 Retrieval Precision 之间寻找平衡

## **5.2 直接绕开这个两难：Parent-Child 检索**

有一个实战中非常常用的解法，它指出了一件容易被忽略的事：**检索粒度和生成粒度本来就不必相同。**

```
用 200 token 的 child chunk 建向量   → 检索精度高（语义集中、噪声少）
命中后，返回其所属的 2000 token parent chunk 给 LLM
                                     ↑ 上下文完整，LLM 不会断章取义
```

所以"chunk 该多大"这个问题，正确的问法是分开的两个问题：

* **用来检索的向量，粒度要多细**（倾向小）
* **送给 LLM 的上下文，粒度要多粗**（倾向大）

## **5.3 chunk 大小策略**

### **5.3.1 Fixed-size Chunking(固定长度切分)：**

每 N token 切分一次

### **5.3.2 Sliding Window（滑动窗口切分）**

如一段文字

```
AAAAAAAAAAAAAAAAAAAAAAAA...
```

按照 chunk\_size = 500 token，overlap = 50 token

> overlap 建议取 chunk 大小的 **10% ~ 20%**（这里的 50/500 就是 10%，是合理值）。
>
> overlap 的作用是**防止语义被切断在边界上**：一句话的前半在 chunk 1、后半在 chunk 2，两个 chunk 的向量都不完整。overlap 让每个 chunk 都"看到"完整的一句话。
>
> 代价是**同一段内容被存了多次**——所以 overlap 越大，存储和去重成本越高。

```
Chunk 1
[--------------------]
​
Chunk 2
          [--------------------]
​
Chunk 3
                    [--------------------]
```

### **5.3.3 Sentence-based（按照句子切分）**

### **5.3.4 Paragraph-based（按照段落切分）**

### **5.3.5 语义结构切分**

对于结构化文档，**按照语义结构切分通常更合理。**

如文档：

```
1. 用户注册
    1.1 手机号注册
    1.2 邮箱注册
​
2. 用户登录
    2.1 密码登录
    2.2 验证码登录
​
3. 商品管理
    3.1 商品创建
    3.2 商品删除
```

不能固定 500 token 一个切分，而要按照

```
Document
   ↓
Section
   ↓
Subsection
   ↓
Paragraph
   ↓
Chunk
```

切分成

```
Chunk 1
标题：用户注册
内容：用户可以通过手机号注册……
​
Chunk 2
标题：用户登录
内容：用户可以通过手机号和密码登录……
```

> ★ 注意这里有个容易被当成"排版美观"的细节：**把标题路径拼进 chunk 内容里，是会影响检索效果的。**
>
> 因为「用户登录 > 验证码登录」这些词原本不在正文里。用户如果直接搜"验证码登录"，正文 chunk 里可能一次都没出现"验证码"三个字，向量和 BM25 都可能漏掉它。拼上标题路径，这个 chunk 才可能被命中。
>
> 更完整的做法是拼**完整路径**而不是单层标题：`"用户登录 > 验证码登录 > 常见问题"`。

## **5.4 小 chunk 的隐藏代价：向量条数暴增**

200 token 一个 chunk，一本 10 万 token 的手册就是 **500 条向量**。

这不是"多占点存储"这么简单——它直接影响：

* 检索延迟（要比较的向量变多）
* 索引大小（前面「索引评价维度」里的 Memory / Index Size）
* 去重难度（overlap 会让相邻 chunk 高度相似，容易出现"召回 5 条其实是同一段话"）

**这是 chunk 大小决策里最常被忽略的一端。**

## **6.1 BM25 关键词检索方法**

它会考虑：

* Query 中的词有没有出现在文档里
* 出现次数
* 词在整个文档集合中的稀有程度
* 文档长度

用公式表示就是：

```
BM25(q, d) = Σ_t  IDF(t) · [ f(t,d)·(k1+1) ] / [ f(t,d) + k1·(1 - b + b·|d|/avgdl) ]
​
k1 ∈ [1.2, 2.0]   → 控制"词频饱和"：出现 100 次 ≠ 比出现 10 次强 10 倍
b  = 0.75         → 控制"文档长度归一化"
```

对照上面四点：

**直觉描述公式中的对应部分**词有没有出现`Σ_t`（只对 Query 中出现的词求和）出现次数`f(t,d)`词在整个文档集合中的稀有程度`IDF(t)`文档长度\`

> 也就是说你的直觉描述和公式是完全对得上的，只是公式给每个直觉配了一个"可调的旋钮"（k1 和 b）。

## **6.2 混合索引如何把两个结果合起来**

假设 Query 分别得到

```
BM25:
A  rank 1
B  rank 2
C  rank 3

vector Search:
C  rank 1
D  rank 2
A  rank 3
```

BM25 得到的分数和 向量相似度分数不能直接对比，实际系统中常用 **RRF(Reciprocal Rank Fusion)**

## **6.3 RRF**

> 不要直接比较两个搜索算法的分数，而比较它们的排名。

```
排名越靠前 → 分数越高
```

然后把多个检索器的排名结果融合.

公式：

```
RRF(d) = Σ_i  w_i / (k + rank_i(d))

k ≈ 60    # 经验值：压平头部差距，防止某个检索器的第 1 名"一票通吃"
w_i       # 各检索器权重，如 BM25 0.3 / 向量检索 0.7
```

以笔记里的例子手算一下（取 k=60，权重都为 1）：

```
          BM25排名   向量排名       RRF 得分
A            1          3        1/61 + 1/63 ≈ 0.0323
B            2          —        1/62       ≈ 0.0161
C            3          1        1/63 + 1/61 ≈ 0.0323
D            —          2        1/62       ≈ 0.0161
```

结果：**A 和 C 并列第一**。这正体现了 RRF 的特点——它不管 BM25 给了 A 多高的分，只认排名，所以"两边都排得靠前"的文档最占优势。

### **6.3.1 RRF 的代价（这才是"理解"而不只是"知道"）**

它**只用排名，丢掉了分数信息**。因此会出现这种情况：

> BM25 给了某文档 50 分（第 1 名，遥遥领先），向量检索给了它 0.95（第 3 名）——这种"高置信信号"在 RRF 里会被抹平成普通的一次排名贡献。

替代方案是**分数归一化后加权求和**（min-max 或 z-score 归一化再融合），保留置信度但需要调参。

**RRF 胜在免调参、跨检索器鲁棒**，所以成为默认选择。

# **7 Rerank（重排序）**

> 重新对 Query 和候选文档之间的相关性进行评分。

## **7.1 Reranker 和 Embedding 有什么区别？**

> 原表述"Rerank 得到的是更准确的答案"不准确：**reranker 输出的是相关性分数，不是答案。**

真正的区别在**模型架构**，而不是"谁更准"：

```
Embedding 模型 = Bi-Encoder（双塔）
  Query → 塔A → q_vec  ┐
                       ├→ 内积/余弦 → 分数
  Doc   → 塔B → d_vec  ┘

  ★ Doc 向量可以离线预先算好并入库 —— 这是它能支撑百万级检索的根本原因
  优点：快（一次内积）
  缺点：Query 与 Doc 从未"见面"，token 级的交互信息全部丢失
```

```
Reranker = Cross-Encoder（交叉编码器）
  [Query, Doc] → 同一个 Transformer 一起编码 → 一个相关性分数

  优点：Query 与 Doc 的每个 token 之间都有 attention 交互，精度显著更高
  缺点：必须逐对现算，无法预计算 → 100 个候选 = 100 次前向推理
```

> 所以"Embedding 让语义相近的文本距离更近"这个描述是对的，但它**没说清为什么它不如 rerank**：不是因为它算的是"相关"还是"答案"，而是因为**双塔结构里 Query 和 Doc 没有任何交互**。

## **7.2 为什么不全部 Rerank？**

因为 Rerank 很慢

> Retriever 必须快，所以牺牲一定精度；Reranker 可以慢，因为它只处理 Retriever 筛出来的一小部分候选。

**但"慢"的根因要说清楚：不是模型大，而是「不能预计算」。**

Bi-Encoder 的 Doc 向量可以提前算好、存进向量库，查询时只做一次内积。Cross-Encoder 必须每来一个 Query，就把所有候选文档逐个重新编码一遍——**这部分计算无法复用，也无法离线做**。

## **7.3 实战配置与延迟预算**

```
向量召回 top 50 ~ 100   →   Rerank 到 top 5 ~ 10   →   送给 LLM
```

延迟预算参考（用于判断瓶颈在哪）：

**环节量级**Query Embedding 调用~20 - 50 ms向量检索~5 - 20 msRerank 50 条~100 - 300 ms**LLM 生成~1 - 3 s**

> 结论：**Rerank 通常不是瓶颈，LLM 才是。** 所以如果端到端延迟不够理想，先看 LLM，而不是砍掉 rerank——砍掉 rerank 通常会让答案质量明显下降，但省下的时间很有限。

# **8 元数据过滤（生产必需）**

> 真实系统里，**向量检索几乎从不单独使用**，一定带过滤条件。

```
where  { tenant_id = "acme", lang = "zh", doc_type = "manual", updated_at > 2025-01-01 }
vector similarity(q, top_k=10)
```

## **8.1 两种执行顺序，性能差异巨大**

**策略做法优点缺点pre-filter**先按条件过滤，再在剩余集合里做向量检索结果准确过滤后剩余数据太少时，HNSW 的图导航会退化成近乎瞎走**post-filter**先做向量检索，再过滤结果快可能出现"搜了 top 100 全被过滤掉，返回 0 条"

**这是向量库选型的一个硬指标**——不是所有向量库都支持高效的 pre-filter。选库时要专门确认。

## **8.2 多租户场景（SaaS / Agent 应用的高危区）**

> **一个 `tenant_id` 过滤条件漏掉，就是数据越权事故。**

这个坑在 Agent 应用里极其常见，因为过滤条件往往是模型生成 tool 调用参数时给出的——**模型可能忘记带，也可能被 prompt injection 诱导改掉**。

所以租户隔离**不能依赖模型正确填写参数**，要在服务端强制注入，或者用物理隔离（每租户独立 collection），而不是只靠一个 `where` 条件。

# **9 Embedding Model 管理**

> RAG 系统里 Embedding Model 不是一个随便换的组件，它和向量库里的向量存在强绑定关系，因此需要管理好模型、版本、维度和迁移。

## **9.1 为什么需要“管理” Embedding Model？**

> 为什么需要“管理” Embedding Model？
>
> Query 和 Document 必须使用兼容的 Embedding Model。

建库的时候

```
文档
 ↓
Embedding Model A
 ↓
1536维向量
 ↓
Vector DB
```

以后用户查询

```
Query
 ↓
Embedding Model B
 ↓
768维向量
 ↓
Vector DB
```

这通常直接就不行。**维度不一样，相似度在结构上就算不了。**

但要补一个更深的区分，见下面「同维度 ≠ 同空间」。

## **9.2 Embedding Model 管理首先管理什么？**

```
Embedding Model
├── model name
├── model version
├── dimension      ← 输出维度（可能可配置，见上文）
├── distance metric ← ★ 最容易漏的一个
├── provider
└── configuration
```

> ★ **`distance metric` 必须一起管理。** 同一个模型在 cosine 和 IP 下检索结果不一定相同（尤其当向量库对 IP 不做归一化时，见「三种度量之间的关系」）。模型换了、metric 忘了换，是一种很隐蔽的故障。
>
> 这个清单的真正用途是：**把它当作向量字段的"身份信息"存进库里**。将来排查"为什么召回突然变差"时，第一个要看的就是它。

## **9.3 不同 Embedding Model 不能随便混用**

假设

```
文档 A → BGE-M3
文档 B → OpenAI Embedding
文档 C → 另一个模型
```

然后全部塞进同一个 vector field, 这通常是不合理的，他们之间的距离没有统一意义

所以通常**一个向量空间对应一个 Embedding Model**

### **9.3.1 ★ 同维度 ≠ 同空间**

假设两个不同模型都输出 1024 维：

```
模型 X → 1024 维向量
模型 Y → 1024 维向量     ← 长度一样，能塞进同一个字段
```

但它们的向量**依然不可比**。维度相同只意味着「数据能装进同一个字段」，完全不代表「距离有意义」。

> 所以真正的障碍是**空间不同**，而不是「长度不同」。"维度不一样就没法算相似度"是个简化说法——维度对不上是**硬性报错**，维度对上了但空间不同则是**静默的错误结果**。后者更危险，因为它不会报错，只会让召回率悄悄变差。

### **9.3.2 实践中的做法**

不同模型的向量不是"塞进同一个字段然后混着查"，而是**各自独立成字段**：

```
文档
├── v_bge_1024        ← 由 BGE-M3 生成，1024 维
└── v_openai_1536     ← 由 OpenAI 生成，1536 维
```

每个字段有自己绑定的模型、维度和 metric。查询时必须指定用哪个字段。

更换 Embedding Model ≈ 需要重新 Embedding 文档，**除非新模型在你现有维度上与其向量空间兼容**（见下一节的例外）。

## **9.4 模型升级怎么办？**

> 不能简单的直接替换模型

### **9.4.1 例外：维度是可配置的**

上一节说"更换模型 ≈ 需要重新 Embedding"，大方向正确，但有一个**必须知道的例外**，否则会做出错误的架构决策：

现代 Embedding 模型的输出维度**是可配置的**（前面「Embedding 模型」一节已写过）：

```
OpenAI text-embedding-3 系列 → dimensions 参数可指定输出维度
阿里云 text-embedding-v4    → 64 ~ 2048（默认 1024）
阿里云 text-embedding-v3    → 512 ~ 1024，且官方声明与 v4 维度兼容
                              → 已有 v3 索引可以直接迁移到 v4
```

修正后的表述：

> 更换 Embedding Model ≈ 需要重新 Embedding 文档，**除非新模型在你现有维度上与其向量空间兼容**（如 v3 → v4 这类官方声明兼容的升级路径）。

**注意这个例外的边界**：它是"官方声明了向量空间兼容"，不是"维度凑巧一样"。前者可以省下全部重新 Embedding 的成本，后者只会让你得到一个静默变差的系统。

### **9.4.2 一次完整的模型迁移长什么样**

```
原始文档
                │
        ┌───────┴────────┐
        ↓                ↓
   Embedding v1     Embedding v2
        ↓                ↓
   Vector DB v1      Vector DB v2
        ↓                ↓
        └───────┬────────┘
                ↓
           A/B 评测对比
```

评测指标：

```
Recall
MRR
NDCG
Answer Quality
Latency
Cost
```

### **9.4.3 迁移的正确姿势：双写 → 对比 → 灰度 → 下线**

```
1. 新模型对新文档双写  →  两个向量库同时存在
2. 用同一批评测集跑两个库  →  对比 Recall / MRR / 成本 / 延迟
3. 灰度切流量  →  观察线上指标
4. 确认后才重新 Embedding 全量历史文档、下线旧模型
```

> 不要"直接替换"的原因很实际：**重新 Embedding 全量文档既贵又慢**。如果新模型效果不如预期，你既付了钱、又退不回去。双写能让你在花这笔钱之前就拿到评测数据。

# **10 检索质量评测**

> 前面「索引」章节里的 Recall / Latency / QPS 是**索引层面**的指标。 这一节是**整条 RAG 检索链路**的评测方法——它才是用来验证"我改的 chunk 大小/混合检索/rerank 到底有没有用"的东西。

## **10.1 最小可用的评测方法**

上面列了 `Recall / MRR / NDCG / Answer Quality / Latency / Cost`，但光有指标名是没法落地的。最小可用流程：

```
1. 手工构造 30~100 条评测集：(问题, 正确答案所在的文档/chunk)
   ★ 这是最容易被跳过、也最不能跳过的一步

2. 离线跑检索，算 Recall@K 和 MRR
   —— 不调 LLM，快且免费，可以反复跑

3. 调参：chunk 大小 / overlap / nprobe / efSearch / top_k / 是否开 rerank
   —— 每个参数都能用 Recall@K 直接量化，不要凭感觉调

4. 再评估端到端 Answer Quality
   —— 这一步才需要 LLM，也才需要人工或 LLM 打分
```

> ★ **Recall 是 RAG 的天花板。** 如果正确文档连检索都没召回来，后面的 rerank 和 LLM 再强也救不回来。
>
> 所以顺序一定是**先测 Recall，再测答案质量**。跳过第 1、2 步直接调 prompt，是最常见的低效做法。

# **11 RAG 全链路**

> 前面所有章节都是"零件"，这一节把它们装成"整机"。
>
> **为什么必须看整机**：只有看清了链路，才知道每一环漏掉之后的失败长什么样。

```
【离线】Indexing
  文档 → 解析 → Chunking → Embedding → 向量库（+ 元数据 + 关键词索引）

【在线】Retrieval + Generation
  用户 Query
    ↓
  ① Query 改写 / 扩展        ← 多轮对话时必需（指代消解）
    ↓
  ② Query Embedding
    ↓
  ③ 混合检索：向量检索 + BM25
    ↓
  ④ RRF 融合
    ↓
  ⑤ Rerank（top 50 → top 5）
    ↓
  ⑥ 组装 Context（引用来源、去重、长度裁剪）
    ↓
  ⑦ LLM 生成
```

## **11.1 每一环漏掉的失败长什么样**

**环节缺失后的症状对应本笔记**① Query 改写多轮对话里"它怎么样？"这类指代型提问全部失效—② Embedding—「Embedding」③④ 混合检索搜错误码、函数名、人名全部失效「混合索引」⑤ Rerank正确文档召回了但没排进 top 5，LLM 看不到「Rerank」⑥ Context 组装检索是对的，但上下文被裁掉了 / 塞进了互相矛盾的多版本—⑦ LLM 生成幻觉、不遵循上下文—

> 注意 ①⑥⑦ 这三环**和向量数据库无关**，但在真实 RAG 里同样是主要失败来源。学了向量库不等于会做 RAG——这正是要画这张图的原因。

# **12 向量检索如何变成 Agent 的工具**

> 这一节直接对应"学习向量数据库是为了做 Agent"这个目标。

RAG 与 Agent 的区别：

```
RAG：  用户问题 → [固定 pipeline] → 答案

Agent：用户问题 → LLM 决策 → 调 tool: search_knowledge_base(query="...")
                            → 看结果 → 可能再调一次 / 换个 query
                            → 或调别的工具 → 生成答案
```

**RAG 是固定管线，Agent 是让模型自己决定要不要检索、检索什么。** 对 Agent 开发者，向量检索需要额外具备这些性质：

## **12.1 检索是一个有 schema 的 tool**

```
参数：query / top_k / filter ...
要求：模型要能正确填写 → 参数名和描述必须清晰、无歧义
```

参数描述写得含糊，模型就会填错 `top_k` 或漏掉 `filter`——这不是模型能力问题，是 tool 设计问题。

## **12.2 返回内容要可控**

不能把 50 个 chunk 全塞回去挤爆上下文。需要在工具内部做 top-k 裁剪、去重、甚至摘要。

> 注意这和你自己的 RAG 管线里的 top\_k 是**两个不同的 top\_k**：一个控制"给模型看多少"，一个控制"工具往对话里塞多少"。Agent 场景下后者通常要更小。

## **12.3 要支持多轮 / 多跳检索**

第一轮检索不到，模型要能改 query 再来一次。这意味着**检索会被串行放大**：

```
单次 RAG：  1 次检索 = 20ms
Agent 多跳：3 次检索 + 3 次 LLM 决策 ≈ 数百 ms ~ 数秒
```

**所以 Agent 场景对检索延迟比 RAG 更敏感**——前面 HNSW 的 `efSearch` 这类"可在线调节的旋钮"在这里就有了直接的工程价值。

## **12.4 ★ 必须有明确的"检索不到"信号**

**这是最重要的一条，也是幻觉的主要来源之一。**

```
❌ 错误做法：检索不到 → 硬塞几个相似度很低的文档 → 模型被迫从无关内容里编答案
✅ 正确做法：返回明确的"未找到相关内容" + 相似度分数 → 模型可以回答"资料中没有"
```

工具返回值里应该带上**相似度分数**和**是否低于阈值**的标记，让模型有机会判断"这些结果不可靠"。

## **12.5 记忆（Memory）本质也是向量库**

对话历史存成向量做长期记忆，用的是完全同一套技术（Embedding + 向量检索 + 元数据过滤）。**你在这份笔记里学的东西，在 Agent 里会被复用两次：知识检索 + 长期记忆。**
