# 多轮对话 RAG

> 单轮 RAG 和多轮 RAG 是**两套工程**——不是"加个历史记录"就完事。
>
> ★ 这一节是 [RAG学习.md](RAG学习.md) 第 12.3 节（多跳检索）在**对话维度**上的展开，也是 [04_Query改写与多路召回.md](04_Query改写与多路召回.md) 里"指代消解"的完整版。
>
> **为什么是下一步**：学习路线 [agent开发学习路线.md](agent开发学习路线.md) 的 Phase 0.4。**也是 Phase 0 里唯一需要新工程结构的一节**——前三节都是"改一个环节"，这一节要引入"状态"。

## 1. 为什么多轮是另一套工程

### 1.1 一个早被验证过的困难

多轮 QA 的困难不是新问题。QuAC 数据集在 2018 年就明确指出了这个挑战：

> 它的提问往往**更开放、可能无法回答、或者只有放在对话上下文里才有意义**。

> —— QuAC: Question Answering in Context

**"只有放在对话上下文里才有意义"** —— 这一句话就是本节要解决的全部问题。

```Plain
单轮：  "退款要几天到账？"              ← 语义自足，可以直接检索
多轮：  "那它呢？"                      ← ★ 单独拿出来，无法检索
        "刚才说的那个例外情况是什么？"     ← ★ 依赖上文
        "换个话题，你们支持哪些支付方式？" ← ★ 前文变成了噪声
```

### 1.2 学术研究其实严重落后于现实

有一篇 2025 年的 benchmark 论文把这件事说得很直白：

> 现有学术研究**绝大多数聚焦在单轮 RAG**，在应对真实应用中多轮对话的复杂性方面**留下了显著空白**。 —— CORAL: Benchmarking Multi-turn Conversational Retrieval-Augmented Generation

> ★ 这句话对你有一个很实际的含意：**多轮 RAG 是一个"工程实践领先于学术"的领域**。
> 所以本节里，论文能给你的主要是**"问题清单"和"评测方法"**，具体怎么搭，还得靠你 [RAG学习.md](RAG学习.md) 里那套工程判断。

### 1.3 ★ 多轮引入了两个单轮不存在的东西

```Plain
① 状态（State）    —— 之前的对话会影响这一次的行为
② 噪声（Noise）    —— 之前的话题会污染这一次的检索
```

> ★ **这两者是矛盾的**：留历史是为了"状态"，但留历史也带来了"噪声"。
> **多轮 RAG 的全部工程难度，就在这个矛盾里**——留多少、留什么、什么时候清空。
>
> 这和你 [RAG学习.md](RAG学习.md) 第 8A 章的"少而精 > 多而杂"是**同一个取舍**，只是从"文档条数"变成了"历史轮数"。

## 2. 四个必须解决的问题

### 2.1 问题一：指代消解（必须做）

```Plain
用户：企业版套餐怎么退款？
助手：（回答）
用户：那它支持开发票吗？          ← "它" = 企业版套餐
```

**不做消解，检索必然失败**——因为"它"这个词在向量空间里没有有效坐标。

> ★ 这一点可以复用你笔记里的结论：**精确标识符、代词在语义空间里没有有效坐标**。
> 见 [RAG学习.md](RAG学习.md) 第 1.2 节「Embedding 保留语义、扔掉字面」。

**做法**：把多轮 query 改写成**不依赖上下文的独立 query**（stand-alone query）。

### 2.2 ★ 问题二：人工标注的改写，不一定是最优的

这是本节最值得记住的一个发现。IterCQR 论文指出：

> 以往会话式 query 改写方法**经常依赖人工标注的改写**。然而，**这些人工构造的 query 往往导致次优的检索性能，且收集成本高昂**。

> —— IterCQR: Iterative Conversational Query Reformulation with Retrieval Guidance

**他们的解法**：不用人工改写，而是**直接拿检索信号（IR signals）当奖励**，迭代训练改写模型。

> IterCQR 的训练引导改写模型，**使得生成的 query 包含前文对话中必要的信息**。

> —— IterCQR: Iterative Conversational Query Reformulation with Retrieval Guidance

#### 为什么这一条对你极其重要

```Plain
直觉：改写 = "把'它'替换成'企业版套餐'"，人工能写对
现实：论文说人工标注反而次优
```

**因为改写的好坏不该由"人读起来通不通顺"判断，而该由"检索结果好不好"判断。**

```Plain
❌ 优化目标：人觉得这句改写"对"
✅ 优化目标：★ 改写后的 query 能让检索器召回正确文档

这两者不一致。人工写"企业版套餐支持开票吗"读起来完全正确，
但它可能漏掉了原文里的关键术语（比如"发票"在文档里写作"开具增值税专用发票"）。
```

> ★★ **给你的直接做法**：你不需要训练模型，但**必须把优化目标摆对**——
> 在评价你的改写 prompt 好不好时，**看 Recall 的变化，不要看改写结果读起来顺不顺**。
> 这正是 [03_RAG评估体系.md](03_RAG评估体系.md) 存在的意义：**用指标代替直觉**。

### 2.3 问题三：话题切换（最隐蔽）

CORAL 明确把 **topic shifts（话题切换）** 列为多轮 RAG 要应对的关键挑战之一。

> —— CORAL: Benchmarking Multi-turn Conversational Retrieval-Augmented Generation

```Plain
第 1~5 轮： 讨论退款政策        → 检索到"退款""时限""渠道"相关文档
第 6 轮：   "你们支持哪些支付方式？"  ← 换话题了
            ↓
   如果还把前 5 轮拼进 query：
   "退款 时限 渠道 支付方式"    ← ★ 旧话题变成了检索噪声
   → 召回一堆退款文档，把"支付方式"的正确文档挤掉
```

> ★ **话题切换的危害是"静默"的**：它不报错，只是让召回质量悄悄变差。
> 这类故障最难查——和你笔记里"维度对得上但空间不同是静默错误"是同一类危险。

**处理方式**（由简到繁）：

| 方式 | 做法 | 代价 |
|---|---|---|
| 规则 | 检测到 query 里没有指代词 → 不拼历史 | 0 |
| ★ **检索结果反馈** | 拼了历史检索分很低 → 退回不拼历史重试 | 一次额外检索（便宜） |
| 小模型判别 | 训一个话题切换分类器 | 需要标注 |
| LLM 判别 | 让 LLM 判断"是否延续话题" | 一次调用 |

> ★ 推荐第 2 种：**"先试一下，看结果再决定"** ——这又是那个模式。
> 它在 [04_Query改写与多路召回.md](04_Query改写与多路召回.md) 4.2 出现过，在 Phase 1 的 Agent Loop 里会成为常态。

### 2.4 问题四：追问 vs 新问题（要不要重新检索）

**这一类问题不该检索**：

```Plain
用户："帮我对比一下企业版和专业版"
助手：（长回答）
用户："你刚才说的第二点再详细讲讲"     ← 答案已经在上下文里了
        ↓
★ 这次检索纯属浪费：既增加延迟，又可能召回无关内容污染上下文
```

**而这一类必须检索**：

```Plain
用户："专业版呢？"                    ← 换了主体，需要新资料
```

> ★ **这个判断本身就是"Agent 化"的开端**——"要不要调工具"是 Agent Loop 的核心决策之一。
> Self-RAG 的"自适应检索"（判断检索是否有必要）走的就是这条路。
> 见 [05_生成prompt与幻觉抑制.md](05_生成prompt与幻觉抑制.md) 第 4 节。

## 3. 历史怎么管

### 3.1 三种策略

```Plain
① 全量保留        简单，但很快爆上下文；且旧话题成为噪声
② 滑动窗口        只留最近 N 轮；简单有效，但会丢失早期关键信息
③ ★ 摘要 + 窗口   早期压缩成摘要，近期保留原文   ← 工业界常用
```

**为什么"摘要 + 窗口"最实用**：

```Plain
早期历史的作用    → 提供背景（"用户问的是企业版"）  ← 摘要就够
近期历史的作用    → 提供细节（具体问了什么、答了什么）← 需要原文
```

> ★ 这个分工和你 [RAG学习.md](RAG学习.md) 的 Parent-Child 是同一个思想：
> **不同粒度服务不同目的** —— 小粒度保证精度，大粒度保证完整。

### 3.2 ★ 但"摘要"这个手段本身有个已知限制

你已经在 [05_生成prompt与幻觉抑制.md](05_生成prompt与幻觉抑制.md) 学过位置效应：

> 性能通常在相关信息出现在**输入上下文的开头或结尾**时最高，而当模型必须在**长上下文的中间**访问相关信息时**显著下降**。

> —— Lost in the Middle: How Language Models Use Long Contexts

**把它套到对话历史上**：

```Plain
[系统提示] [早期摘要] [第3轮] [第4轮] [第5轮] [第6轮] [当前问题]
    ↑          ↑                              ↑
  开头        靠前                          结尾
                ★ 中间那几轮最容易被忽略
```

> ★★ **所以"多留几轮"和"把 20 条文档全塞进去"是同一个错误** —— 中间的内容等于没放。
> **结论：窗口不要贪大**。留 3~5 轮通常就够，多留只是在给模型的"中间遗忘区"喂料。

### 3.3 历史 vs 当前 query 的权重

```Plain
❌ 直接把历史文本拼在 query 前面
   "退款 时限 企业版 那它支持开发票吗"     ← 语义被稀释

✅ 先改写成独立 query
   "企业版套餐支持开发票吗"                ← 语义集中
   然后只用它检索
   （历史只在"改写"这一步用到，不进检索）
```

> ★ **这是一个关键区分**：历史是**改写的输入**，不是**检索的输入**。
> 混在一起，你就同时引入了状态和噪声——而噪声正是你在 2.3 里想避免的。

## 4. 如何评测多轮 RAG

### 4.1 单轮评测集会骗你

你 [03_RAG评估体系.md](03_RAG评估体系.md) 建立的评测方法假设"一问一答"。**多轮下会系统性高估**：

```Plain
单轮评测：  "企业版支持开发票吗？"  → 检索良好 → Recall 高
多轮真实：  "那它支持开发票吗？"    → 缺消解 → 检索失败

★ 你的单轮评测集永远测不出后者的失败
```

### 4.2 CORAL：一个现成的多轮 benchmark

CORAL 是专为**真实多轮对话场景**设计的大规模 benchmark，它明确覆盖了这些挑战：

> **开放域覆盖、知识密集、自由形式回答、以及话题切换（topic shifts）**。

> —— CORAL: Benchmarking Multi-turn Conversational Retrieval-Augmented Generation

**它支持三项核心任务**（正好覆盖你学过的三条线）：

| CORAL 的任务 | 对应你学过的 |
|---|---|
| **passage retrieval**（段落检索） | [04_Query改写与多路召回.md](04_Query改写与多路召回.md) |
| **response generation**（回答生成） | [05_生成prompt与幻觉抑制.md](05_生成prompt与幻觉抑制.md) |
| **citation labeling**（引用标注） | [05](05_生成prompt与幻觉抑制.md) 2.2 的 ALCE |

> ★ 它同时提出**一个统一框架来标准化各种多轮 RAG 方法**，并做了全面评测，结论是**现有方法有大幅改进空间**。
> —— CORAL: Benchmarking Multi-turn Conversational Retrieval-Augmented Generation

> ★★ **给你的直接建议**：**不要自己从零设计多轮评测集**——先跑 CORAL，看你的系统在标准化任务上什么水平。
> 这比你拍脑袋造 30 条多轮问答靠谱得多，而且**结果可比**。

### 4.3 ★ 多轮评测必须单独建，不能复用单轮

```Plain
需要单独覆盖的场景：
├─ ★ 纯指代型：「那它呢」「刚才那个」
├─ ★ 指代 + 省略：「专业版」（省略了"支持开发票吗"）
├─ ★ 话题切换：「换个话题，……」
├─ ★ 追问（不该检索）：「第二点再展开讲讲」
└─ ★ 指代回到很早的轮次：「回到第一个问题」

★ 最后一类特别容易被忽略：指代不一定指向【上一轮】
```

> ★ 评测集里这几类要**分别统计**，不能混成一个平均分——
> 因为它们的失败原因完全不同（消解失败 / 话题污染 / 该不该检索）。
> 这和 [03_RAG评估体系.md](03_RAG评估体系.md) 3.3 的"按归因分组看"是同一个方法论。

## 5. 最小可跑的实现

```Plain
# 伪代码：体现决策而非具体 API

def multi_turn_rag(session, user_input):

    # ---------- 第 1 步：判断是否需要检索（★ 用便宜的方式） ----------
    if is_followup_about_previous_answer(user_input, session.last_answer):
        # "第二点再展开讲讲" 这类：答案已在上下文里
        return llm_continue(session.messages, user_input)
        # ★ 不检索，省一次检索 + 避免噪声

    # ---------- 第 2 步：改写成独立 query（历史是【改写】的输入） ----------
    history = session.recent(3)          # ★ 只取最近 3 轮，别贪多（见 3.2）
    standalone = llm(
        "把用户最新的问题改写成不依赖上下文、可独立检索的问题。\n"
        "如果最新问题本身已经自足，原样返回。\n\n"
        f"对话历史：\n{history}\n\n最新问题：{user_input}"
    )

    # ---------- 第 3 步：检索（★ 只用 standalone，不拼历史） ----------
    results, scores = retrieve(standalone)

    # ---------- 第 4 步：★ 话题切换检测（用检索结果反馈） ----------
    if max(scores) < LOW_SCORE_THRESHOLD and len(history) > 0:
        # 拼了历史的改写可能被旧话题污染 → 退回用原始 query 重试
        results2, scores2 = retrieve(user_input)
        if max(scores2) > max(scores):
            results, scores = results2, scores2   # 说明确实换话题了
            # ★ 并且考虑：清空/降权历史（话题已切换）
            session.mark_topic_switch()

    if not results:
        return "资料中没有找到相关内容。"     # 见 8A.4

    # ---------- 第 5 步：组装（复用 8A） + 生成（复用 05） ----------
    context = assemble(standalone, results, scores)
    answer  = answer_with_cove(standalone, context)   # 见 05 第 7 节

    # ---------- 第 6 步：记录（★ 为归因留证据） ----------
    session.append({
        "user": user_input,
        "standalone": standalone,        # ★ 必存：改写前后都要留
        "retrieved": results,
        "answer": answer,
        "topic_switch": session.topic_switched,
    })
    return answer
```

**六个不要省的点**：

```Plain
1. ★ 存"改写前 vs 改写后" —— 否则出了错无法判断是改写坏了还是检索坏了
2. ★ 历史只进【改写】，不进【检索】 —— 否则同时引入状态和噪声
3. ★ 窗口别贪大（3~5 轮） —— 中间的轮次等于没放（Lost in the Middle）
4. ★ 用"检索分低 → 退回重试"检测话题切换 —— 比训分类器便宜得多
5. ★ 追问型问题不检索 —— 省成本、避免污染
6. ★ 多轮评测要单独建，不能拿单轮评测集凑
```

## 6. 什么情况算"这一步做完了"

```Plain
□ 指代消解能跑通："那它呢" 能被改写成独立 query
□ 能说清"历史是改写的输入，不是检索的输入"
□ ★ 有话题切换的处理（至少是"检索分低就退回"这一档）
□ ★ 能识别"追问型问题"并跳过检索
□ 历史窗口有上限，且能说出为什么是 3~5 轮（位置效应）
□ ★ 单独建了覆盖 5 类场景的多轮评测集，且分类统计
□ 跑过 CORAL 或同类标准 benchmark，知道自己什么水平
□ ★ 用 03 的方法量化过：多轮改写让 Recall 从 X 到 Y、成本增加多少
```

> ★ 最后两条是关键：**多轮 RAG 的成本一定更高**（改写 + 可能重试），
> **所以你必须能回答"这个成本换来了多少准确率"**——否则就是在为复杂度买单。

> ★ 一句话总结：**多轮 RAG 的全部难度，在于"历史既是状态又是噪声"这个矛盾**——
> 指代消解要用历史，话题切换要防历史；所以正确的结构是**历史只进改写、不进检索**，并且**用检索结果反过来检测话题切换**。
>
> 而 2.4 的「这次要不要检索」这个判断，会让你的 RAG 第一次拥有"决策"——**那就是 Agent 的起点**。
