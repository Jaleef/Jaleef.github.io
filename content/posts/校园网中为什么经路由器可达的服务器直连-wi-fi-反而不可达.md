## **摘要**

本文激励并分析了一次校园网环境下网络可达性问题：一台连接校园网无线网络 `NWPU-FREE` 的服务器（IP 10.71.29.93），在我的电脑通过一个路由器局域网接入时可以正常 `ping` 通，但当我的电脑直接连接 `NWPU-FREE` 时却无法 `ping` 通。本文从网络基础概念出发，逐步排查，最终定位原因为：两种接入方式下，数据包的源 IP、转发路径及所经过的安全策略不同。通过路由器访问时，路由器执行了 NAT，服务器看到的是路由器 WAN 口的校园网 IP；而直连 `NWPU-FREE` 时，我的电脑作为无线客户端，可能受到 AP 隔离、VLAN 划分、ACL 限制或服务器防火墙策略的影响。本文总结了相关知识点，并给出了排查方法与解决方案。

## **1 引言**

### **1.1 背景**

校园网通常由多个 VLAN、无线接入点、认证系统和防火墙组成，网络策略复杂。我有一台服务器，它通过无线网卡连接校园网 `NWPU-FREE`，并获得了一个固定的私有 IP 地址 `10.71.29.93`。我的电脑有两种上网方式：

* **方式 A**：电脑连接一个“校园网下的路由器”的局域网，通过该路由器接入校园网。
* **方式 B**：电脑直接连接校园无线网络 `NWPU-FREE`。

在方式 A 下，我可以正常 `ping` 通 `10.71.29.93`；在方式 B 下，`ping` 却失败。这让我感到困惑：同样是访问同一个服务器，为什么换个接入方式就不通了？

### **1.2 问题定义**

核心问题：

> 同一台服务器 `10.71.29.93`，为什么经路由器能 `ping` 通，而电脑直连 `NWPU-FREE` 却不行？

这个问题涉及 IP 分配、NAT、路由、VLAN、ACL、AP 隔离、防火墙等多个网络概念。本文旨在通过排查与知识梳理，解释这一现象。

## **2. 预备知识**

在分析问题前，先复习一些关键概念。

### **2.1 IP 地址、子网与网关**

* **IP 地址**：网络中设备的唯一标识，如 `10.71.29.93`。
* **子网掩码**：用于判断两个 IP 是否在同一子网。例如 `255.255.255.0` 表示前 24 位是网络号。
* **网关**：当目标 IP 不在同一子网时，数据包需要发送给默认网关，由路由器转发。

若服务器 IP 为 `10.71.29.93/24`，则其所在子网为 `10.71.29.0/24`，可用地址范围 `10.71.29.1 ~ 10.71.29.254`。

### **2.2 路由器、NAT 与源 IP 变化**

路由器连接不同网络。当电脑通过路由器上网时，电脑通常获得一个内网 IP（如 `192.168.1.2`），路由器 WAN 口获得校园网 IP（如 `10.71.x.x`）。电脑发出的数据包经过路由器时，路由器会执行 **NAT（网络地址转换）**，将源 IP 从 `192.168.1.2` 改为路由器 WAN 口的 IP。

因此，服务器看到的源 IP 是路由器的 WAN IP，而不是电脑的内网 IP。

### **2.3 DHCP 与静态 IP**

设备获取 IP 的方式主要有：

* **DHCP 动态分配**：自动获取，租期有限，可能变化。
* **DHCP 保留（静态绑定）**：根据 MAC 地址每次分配同一个 IP。
* **静态 IP**：管理员手动配置，固定不变。

服务器通常需要固定 IP 以便被访问，因此可能采用静态配置或 DHCP 保留。`10.71.29.93` 就是校园网分配给/配置给该服务器无线网卡的地址。

### **2.4 VLAN、ACL 与 AP 隔离**

* **VLAN**：逻辑上划分网络，不同 VLAN 默认不能直接通信，需经路由和 ACL 控制。
* **ACL（访问控制列表）**：网络设备上的规则，决定允许或拒绝哪些流量。
* **AP 隔离 / 客户端隔离**：无线网络中，同一 SSID 下的终端默认不能互相访问，以防止攻击和扫描。

校园网常将无线用户、服务器、有线用户划分到不同 VLAN，并设置 ACL 限制互访。

### **2.5 ICMP 与 ping**

`ping` 使用 ICMP 协议，发送 Echo Request，期待 Echo Reply。`ping` 不通可能因为：

1. 请求未到达目标；
2. 目标收到但不回；
3. 回包被拦截；
4. 没有路由。

2. **服务器明确拒绝了回包**

   服务器并没有回复 `ICMP echo reply`（正常的 ping 回应），而是回复了 `ICMP host unreachable`（主机不可达）。这非常关键，它说明：

## **4 结果与根因分析**

### **4.1 通过路由器能 ping 通的原因（NAT 掩盖了路由问题）**

1. 电脑位于路由器局域网内，IP 为 `192.168.x.x`。

2) 路由器 WAN 口接入校园网，获得校园网 IP（假设为 `10.71.x.x`）。

3. 电脑访问 `10.71.29.93` 时，路由器执行 NAT，将源 IP 改为路由器 WAN 口的 `10.71.x.x`。
4. 服务器收到请求后，发现源 IP 是 `10.71.x.x`，与自己处于同一网段（或服务器路由表中有到达 `10.71.x.x` 的路由），于是**能够正常回复**。
5. 因此 ping 成功。

### **4.2 直连 NWPU-free 不能 ping 通的原因（非对称路由/回程路由缺失）**

1. 电脑直连 `NWPU-free`，获得无线网段 IP `10.31.153.245`。
2. 电脑发起的 ping 请求，源 IP 是 `10.31.153.245`。
3. 请求成功到达服务器（抓包证明）。
4. 服务器尝试回复 `10.31.153.245`，但在服务器的路由表中，**没有到达 `10.31.0.0/16`（或具体 `10.31.153.0/24`）的路由条目**。服务器的默认网关可能拒绝转发，或者服务器不知道如何把包送回无线网段。
5. 服务器因此回复 `ICMP host unreachable`，导致 ping 失败。

### **4.3 根本原因**

**不是入站被拦截，而是回程路由不通（非对称路由），或者服务器防火墙主动拒绝。**

这也解释了为什么直连无线时会有“同网段不能互访”的错觉——实际上是服务器不知道如何把数据送回无线网段。

## **5. 解决方案**

基于第 4 节定位的根本原因——**服务器回程路由缺失或防火墙主动拒绝**，解决方案可以从服务器侧、临时规避和长期方案三个层面展开。

### **5.1 服务器侧调整（针对根因）**

由于问题出在服务器收到请求后无法回包，因此核心是修复服务器的回程路由或防火墙策略：

1. **检查服务器路由表** 在服务器上执行：
   ```
   ip route
   ```
   查看是否存在到达无线网段（如 `10.31.0.0/16` 或 `10.31.153.0/24`）的路由条目。若没有，说明服务器不知道如何将数据包送回无线客户端。
   * 若服务器默认网关配置正确，但依然没有到达无线网段的路由，说明校园网核心设备未向服务器所在 VLAN 下发该网段的路由。
   * 可尝试手动添加静态路由（需管理员权限）：
     ```
     sudo ip route add 10.31.0.0/16 via <服务器默认网关>
     ```
2. **检查服务器防火墙** 执行以下命令查看是否有拦截 ICMP 或回程流量的规则：
   ```
   sudo iptables -L -n -v
   sudo ufw status
   ```
   若发现有 `REJECT` 或 `DROP` 规则，可临时关闭防火墙测试：
   ```
   sudo ufw disable
   # 或
   sudo iptables -F
   ```
   注意：生产环境中请谨慎操作，测试后需恢复规则。
3. **确认服务器网络接口与网关** 若服务器同时有有线和无线网卡，检查是否因多网卡导致路由表混乱。执行 `ip route` 确认默认路由指向正确的网关。

### **5.2 临时规避方案**

* **继续使用路由器局域网访问服务器**：这是当前最省事的方案。路由器 NAT 将源 IP 转换为服务器可达的校园网 IP，完美绕过了回程路由问题。
* **使用手机热点**：不推荐，因为热点通常也会引入新的 NAT 和策略，且可能不稳定。

### **5.3 长期方案**

* **VPN**：在服务器上搭建 VPN（如 WireGuard、OpenVPN），电脑通过 VPN 接入服务器内网，源 IP 变为 VPN 虚拟网段，服务器回程路由由 VPN 管理，不再依赖校园网路由。
* **SSH 隧道**：若服务器开放 SSH，可通过端口转发访问服务，绕过 ICMP 层面的限制。
* **Tailscale / ZeroTier**：组建虚拟局域网，这些工具自动处理 NAT 穿透和路由，不受校园网 VLAN/ACL 影响。
* **联系网络中心**：确认服务器所在 VLAN 是否允许回程到无线用户 VLAN。若不允许，申请放行策略或调整服务器网关配置。

## **6. 讨论**

本文从一次看似“无线隔离”的连通性问题出发，通过 `tracert` 和 `tcpdump` 的层层排查，最终定位为 **非对称路由（Asymmetric Routing）导致的回程路由黑洞**。这一过程带来了几点重要的启示：

1. **“ping 不通”不等于“请求没到”** 很多人习惯将 `ping` 失败归因于“对方拦截了请求”或“网络不通”。但抓包证明，请求成功到达了服务器，只是服务器不知道如何回复。这种“单向可达”在跨 VLAN、跨网段的网络环境中非常常见。
2. **NAT 掩盖了路由问题** 路由器 NAT 不仅改变了源 IP，还间接掩盖了服务器回程路由的缺陷。当源 IP 是路由器 WAN 的校园网 IP 时，服务器有路可回；当源 IP 是无线网段的 `10.31.153.245` 时，服务器无路可回。这说明 **NAT 在某些场景下是一种“隐式修复”**，但也可能让人误判网络策略。
3. **`tracert` 的局限性** `tracert` 第 5 跳后的超时，容易被误读为“被防火墙拦截”。实际上，中间路由器不响应 ICMP 超时报文是常见的安全策略，并不意味着数据包没有到达目的地。只有结合服务器端抓包，才能得出准确结论。
4. **校园网策略的复杂性** 校园网通常由多个 VLAN、ACL、防火墙和认证系统组成。无线用户 VLAN 与服务器 VLAN 之间的路由策略往往由网络中心统一管理，个人用户难以更改。因此，采用 VPN 或隧道是较为实际的长期方案。
5. **排查方法论** 本文的排查路径可总结为：**现象描述 → 本机配置检查 → 路由追踪 → 服务端抓包 → 对比接入方式 → 根因定位**。这一方法论适用于大多数“单向可达”或“跨网段不通”的网络问题。

## **7 结论**

同一台服务器 `10.71.29.93`，经路由器能 `ping` 通而电脑直连 `NWPU-free` 却不能，根本原因并非校园网拦截了入站请求，而是：

* **经路由器访问时**：路由器执行 NAT，将源 IP 转换为服务器可达的校园网 IP。服务器收到请求后，能够沿原路径回包，因此 `ping` 成功。
* **直连 `NWPU-FREE` 时**：电脑获得无线网段 IP `10.31.153.245`。请求成功到达服务器，但服务器路由表中缺少到达 `10.31.0.0/16` 网段的路由，或防火墙主动拒绝回包，于是回复 `ICMP host unreachable`，导致 `ping` 失败。

因此，问题的本质是 **非对称路由导致的回程路由黑洞**，而非简单的无线隔离或 ACL 拦截。解决方案包括：服务器侧添加静态路由或调整防火墙、临时继续使用路由器访问、长期采用 VPN 或 Tailscale 等虚拟局域网工具，或联系网络中心申请策略放行。
